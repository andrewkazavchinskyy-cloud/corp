## Request

Fix corp#39 (regression follow-up to #21): workshop.json has no real
interprocess transaction, so CLI, web workshop, Telegram, and orchestrator
writers can lose each other's updates or race a corrupt write.

## Outcome

- `bin/corp` gained one shared atomic path: `update_workshop(mutate)` takes
  an `flock`-based lock on a sibling `workshop.json.lock`, re-reads the file
  fresh under that lock, runs `mutate(data)`, then writes via temp file +
  `fsync` + `chmod 0600` + `os.replace` in the same directory.
- Added `set_queue_status(repo, number, to, expect=..., **extra)` — the
  reusable primitive for "move one queue row, only if it's still in the
  expected state," used by both `bin/corp` and `workshop/app.py`.
- Converted every prior `load_workshop()` → mutate → `save_workshop()` pair
  (registry fallback, slots, catalog probe, drafts, tg_offset, orch state,
  queue add/rm/set_running/reconcile) to the shared path.
- `queue_add` now does its dup-check + append inside one locked mutate on a
  fresh read, closing the original lost-append race; label/comment network
  calls moved after the write so the lock is never held across them.
- `workshop/app.py`'s `queue_tick`/`_queue_job` no longer hold a stale
  in-memory `data` blob across `get_issue`/`remove_labels` network calls —
  each transition re-verifies the row is still `waiting`/`running` via
  `set_queue_status` at write time.
- Invalid current JSON now raises `CorpError` and leaves the file untouched
  instead of silently reinitializing to defaults.
- New regression test in `workshop/test_logic.py`: 6 real OS processes
  (`multiprocessing`, fork) hammer a shared counter and 6 distinct queue
  rows through `update_workshop`/`set_queue_status`; asserts no lost
  increments, every row's own update survives, and file mode stays 0600.
  Also asserts corrupt JSON is rejected by both `load_workshop()` and
  `update_workshop()` without being overwritten. Passed 3x locally plus
  once against the deployed `workshop-venv` interpreter.

## Decisions

- Found and fixed a bug in my own first draft of `update_workshop`: "mutate
  returns None → return the full dict" silently broke `set_queue_status`'s
  use of `None` as a "row not found" sentinel. Fixed by making
  `update_workshop` return exactly what `mutate` returns, no magic; the two
  callers that wanted the full dict (`load_workshop`, `queue_set_running`)
  now `return data` explicitly from their own mutate.
- Kept `fcntl.flock` (POSIX stdlib) rather than a third-party lock library —
  matches the issue's "no dependency" constraint and this stack is
  VPS/Mac-only.
- Did not touch queue row format, storage engine, or UI/UX for this issue —
  out of scope per the issue's own "Не делать" list.

## Request

Fix corp#41: isolate writing agents from control-plane secrets and state
(they ran as the same OS user as the workshop, inheriting its full env and
same-UID filesystem access to Telegram token, `workshop.json`, session DB).

## Outcome

- `launch_agent()` in `bin/corp` now always routes the agent CLI argv
  through `wrap_isolated()`: **isolated** mode (once `CORP_AGENT_USER` is
  provisioned) switches OS user via a fixed root-owned wrapper
  (`deploy/corp-agent-exec`) with a from-scratch minimal env and separate
  `$HOME`; **transitional** mode (default, nothing provisioned) keeps the
  same OS user but strips `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` from the
  child's env — verified end-to-end that a spawned process cannot see the
  token even when the parent has it.
- Added `deploy/provision-agent-identity.sh` (idempotent root script:
  creates `corp-agent`, a shared `corp-write` group scoped to
  `CORP_WORKSPACE` only, installs the wrapper to `/usr/local/sbin`, and a
  narrow sudoers NOPASSWD rule) and `deploy/agent-isolation-smoke.sh` (the
  issue's required smoke check: agent identity can write in the workspace,
  cannot read `~/.config/corp/{env,workshop.json,workshop.db,
  workshop-setup-token}`).
- Full runbook in `docs/AGENT_ISOLATION.md`. `corp doctor` and the
  workshop Map tab now surface an `agent identity isolated` check.

## Decisions

- Did not attempt to create the actual `corp-agent` OS user or install the
  sudoers rule: this session has no root/passwordless sudo on the VPS
  (`corp` user only). Provisioning and live smoke verification are a
  documented manual root step, not something an agent session can do.
- Left corp#41 open (commented with what's done vs. the manual step) rather
  than closing it — the issue's "Готово когда" checklist requires a real
  separate UID, which is not true yet.
- A `$HOME`-only redirect without a different UID does not count as
  isolation (same-UID processes always get owner file permissions) — the
  issue's own "Не делать" list already ruled this out, confirmed while
  designing the fallback so transitional mode only ever claims to close
  the env-vector leak, never the filesystem one.
- Wrapper script installed outside `/opt/corp` (root-owned, in
  `/usr/local/sbin`) because `/opt/corp` itself is writable by the `corp`
  user (writing agents edit it when the target project is `corp` — this
  session is a live example) and a corp-writable sudoers target would
  defeat the boundary.

## Open questions
